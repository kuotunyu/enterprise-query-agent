# Enterprise Query Agent v1 設計

日期：2026-09-14。方向已獲使用者同意；以下為 v1 的具體設計基線，尚無實作或實驗成果。

## 1. 目的與選擇

讓營運使用者用中文查詢歷史電商資料，清楚知道答案採用的定義、資料期間與限制。核心難點是關聯資料規劃與答案語意正確性。

考慮三種產品做法：

- 固定問題選單：最容易核對，但自然語言與組合查詢能力有限；保留作 baseline。
- 直接生成 SQL 的聊天介面：彈性較大，但需量測口徑混用與 join 重複計算；保留作 baseline。
- **採用：模型先產生受限的業務查詢計畫，由程式驗證／編譯，再執行與產生有依據的答案。** 限定領域，但能清楚界定正確性責任。

主方法是有限 semantic planner，不宣稱通用自主 SQL Agent。它可以組合支援的指標、維度、期間與比較，但不增加任意程式碼執行能力。

## 2. v1 範圍

使用情境：單人在本機操作歷史 Olist 資料；中文介面。資料庫固定 MySQL 8.4。後端 Python 3.12、FastAPI、Pydantic；SQL 驅動 PyMySQL；SQL 結構檢查使用具 MySQL dialect 支援的 parser（預設 SQLGlot，鎖版本並以測試確認實際支援）。前端由 FastAPI 提供 HTML／CSS／JavaScript；先完成清楚可操作的產品。

不加入登入、多租戶、支付、資料寫回、RAG 平台、微調、多 Agent、第二 SQL 引擎或 GPU serving。這些不是 v1 欠件。

預設執行界限：每筆使用者任務最多 2 輪澄清、3 次模型呼叫、3 條業務 SELECT；每條 SQL 上限 5 秒，任務上限 60 秒；結果最多 200 列。修正失敗計畫也計入同一額度，不無限重試。這些是產品初始限制；若開發題證明不合理，可在正式版本凍結前記錄調整，凍結後三方法使用相同限制。

60 秒任務上限計算服務實際處理時間，暫停計算等待使用者澄清的時間；整段互動經過時間另記錄。三方法使用相同規則，不能用使用者打字速度決定模型 timeout。

模型使用單一 API provider/model，具體模型、參數、價格依實作當日可用設定填入 run manifest。無憑證時使用 deterministic mock；mock 結果不是模型能力證據。模型比較與 4090 本機部署不屬首輪交付。

## 3. 來源與獨立資料環境

來源 repo：kuotunyu/mysql-ecommerce-analytics，commit `619ad706c35951bd6b811ac56765d6ad097ddbaa`。

已查閱 schema.sql、analysis/00_views.sql、sql/01_monthly_revenue.sql、sql/05_repurchase_rate.sql、sql/09_payment_installments.sql、results/SQL_REPORT.md、scripts/fetch_data.py、docker-compose.yml。

- 九份 CSV 對應九張來源表；另有 geolocation_zip 衍生表、v_order_gmv 與 v_order_review views。
- DATETIME 是來源的當地時間欄位，無可靠時區語意；不能當成 UTC 再轉台灣時間。
- 金額使用 DECIMAL／Decimal，輸出 BRL；不要混用二進位浮點與新台幣。
- 新案使用独立 Compose project、容器、port 與 volume；預設 DB port 3307，web port 8010，衝突時報錯並顯示設定入口，不停止其他服務。
- 來源 schema 有 DROP TABLE，來源 compose 固定舊容器名；不得對正在使用的前作環境執行。新案匯入工具只接受本專案識別的獨立環境。
- 可從指定本機 CSV 來源讀取並匯入新 DB，不修改來源 CSV。記錄每檔 SHA-256、row counts、schema 與 ETL 版本。取用或複製前作程式時保留 MIT 授權／出處。
- 不複製前作 .env、憑證、虛擬環境、模型與原始執行紀錄。合成小資料與真實資料報告清楚分開。

獨立 bootstrap 管理者負責 schema／import；應用執行帳號只被授予必要表／view 的 SELECT。应用啟動時核對 DB 身分與權限，不能以管理者連線繼續服務。

## 4. 業務定義

以版本化 catalog 記錄每個指標的粒度、population、時間欄位、null 與分母規則；下列定義是 v1 基線。

| 指標 | 定義與可用維度 |
|---|---|
| gmv | delivered 訂單的商品金額＋運費；按訂單、月份、客戶州、賣家、品類。品類／賣家從 item 粒度加總，不能把整單 GMV 重複分配給每一品類 |
| merchandise_value | 同一 delivered population 的商品金額，不含運費；可用維度同 gmv |
| payment_value | 付款紀錄金額，以付款列加總，期間依所屬訂單 purchase timestamp；v1 明示全部訂單狀態，不稱會計已實現營收；不與 GMV 強制相等。不支援按品類／賣家分攤付款 |
| delivered_order_count / aov | delivered 訂單數；AOV＝同一 population 的 gmv／distinct orders。品類／賣家下的訂單可重疊，必須揭露不可直接相加 |
| late_rate | delivered 且實際／預估送達時間皆有值的訂單中，actual > estimated 的比例；依來源 DATETIME 比較，回傳 eligible、late、missing 三種計數 |
| repeat_customer_rate | 指定 purchase 期間內，至少兩筆 delivered 訂單的 customer_unique_id／至少一筆的 customer_unique_id；不是終身回購率或指定天數 retention |
| average_review_score | 同一 delivered population 的每訂單最新 review_score 平均；依 creation date、answer timestamp、review_id 倒序選一筆；列出有效分母與缺評數 |

「營收」沒有已確認口徑時澄清；同一任務已確認過的口徑保存在 session state，不反覆詢問。不同任務可顯示前次設定，但不得悄悄沿用。

時間用半開區間 [start, end)。使用者說「上個月」時以可見的 as_of_date 解讀；超出資料範圍就說明，不能偷偷改成資料最後一個月。預設 as_of_date 為執行日，展示案例可固定但需標示。

前作將 2017-01 至 2018-08 標為可比較完整月。新案把它記成來源分析採用的 coverage policy，不當成獨立證實的資料完整性。跨出此範圍顯示 partial／unknown；月增率只對相鄰且 policy 允許的月份計算。前期為零則比例為 undefined，仍可顯示絕對變化。

缺品類翻譯用原葡文，缺品類標為 unknown，LEFT JOIN 不丟資料。評論相關只使用 score／時間／識別欄位，不把自由文字評論送給模型。商品成本、毛利、廣告花費、2026 年即時營運均無來源支持，明確說明無法回答。

## 5. 請求與答案流程

1. QuestionRequest 接收 question、session_id、as_of_date；伺服器決定 dataset_id，不採用模型任意指定的資料庫。
2. PlannerDecision 只允許 clarify、query、unsupported 三種動作。clarify 回傳可回答的問題與選項；query 回傳 QueryPlan。
3. QueryPlan 包含 metric_ids、dimensions、filters、time_range、comparison（none／previous_period）、sort、top_k、catalog_version。filter 欄位／operator／value type 均依 catalog 驗證，值採參數綁定；没有 raw SQL escape hatch。
4. 程式驗證可用組合與分母，編譯必要 SQL。比較期間與品類分解可用最多三條查詢。新的 plan revision 使前一版未完成結果失效。
5. 所有 SQL，包括 direct-SQL baseline，都經同一 SQL policy 與 DB executor。通過後取 QueryResult，再由程式計算衍生值與 AnswerFact。
6. AnswerEnvelope 回傳 status、facts、table、definition、population、time_range、coverage、limitations、evidence。數字由可追溯 facts 決定，不讓模型任意生成無來源數字。

QueryResult 保存 query_id、parameterized SQL、參數、欄型、列數、是否截斷、elapsed_ms、資料版本與結果雜湊。AnswerFact 保存 value、unit、result reference 與必要運算。UI 可展開 SQL 與來源；不能只給一個無法定位內容的 hash。

status 至少區分 answered、needs_clarification、unsupported、empty、rejected、timeout、provider_error、execution_error。空資料、無法計算比率與數值零分開。網路重送使用同一 request_id 取既有狀態，避免自動重复付費呼叫；不宣稱 provider 端 exactly-once。

## 6. SQL 與執行控制

SQL policy 使用 parser 檢查單一 SELECT／非遞迴 WITH SELECT、解析 CTE 與實際資料表依賴、允許表欄與函式。初始拒絕 DML／DDL、多語句、SELECT INTO、locking clauses、外部檔案函式、SLEEP／BENCHMARK／鎖函式、使用者變數、未知函式及其他 schema。不能只靠字串開頭或關鍵字 regex。

Runtime 沒有 FILE、EXECUTE、寫入或管理者權限；client 關閉 multi-statements 與 local infile。Bootstrap 憑證不進 web process。SQL 格式檢查、唯讀 DB 權限與資源界限是不同層，分開測試。

5 秒上限必須透過 MySQL 支援的 statement execution limit 及 client deadline 驗證；LIMIT 200 不能限制聚合掃描成本。不要以可被模型覆寫的 hint 或只在畫面停止等待當成取消完成。專用測試環境驗證 timeout 後不留下持續查詢，必要時從服務端取消自己的連線查詢；不授予可終止其他專案連線的通用工具。

參考官方文件：[SELECT](https://dev.mysql.com/doc/refman/8.4/en/select.html)、[optimizer hints](https://dev.mysql.com/doc/refman/8.4/en/optimizer-hints.html)。實作時依選定 parser／driver 的官方文件與 integration tests 確認支援範圍。

## 7. 介面

單頁工作台：可見資料集／coverage／as_of_date，問題輸入、澄清選項、答案摘要、結果表、口徑與限制、展開證據。首次使用有六個開發示例，標示為示例而非評估成績。可取消等待，顯示執行狀態與錯誤；鍵盤可完成整條流程。

來源資料與查詢結果作為純文字渲染，避免內容變成 HTML 或指令。長查詢與所有技術細節放在證據區，不妨礙營運使用者閱讀結果。

## 8. 評估設計

開發階段先完成 acceptance-v1 的公開合成案例與至少 24 個中文業務問題；既有 Olist 十題一律算開發資料。

在模型流程凍結後，另製作 40 個保留業務任務：20 個可直接回答、8 個需澄清、6 個缺資料／超出範圍、6 個拒絕／限制情境。每題帶 question、category、metric/population/time contract、必要澄清腳本、expected terminal status、expected answer facts。另對其中 12 個涉及聚合／join／分母的任務，各用兩個合成資料變體。變體是相依觀察，不當成新增獨立題數。

保留題由不修改候選實作的獨立評估 session 在凍結後編製並封存；同一作者／AI 參與設計的限制如實說明，不稱獨立人類盲測。題目不能是只換名稱的開發題。人工或獨立計算檢查 gold，不用候選 compiler 當唯一 gold generator。LLM-as-judge 只能輔助自然語言檢查，不能取代資料答案。

比較 A 固定模板＋slot extraction、B 模型直接 SQL、C semantic planner＋compiler。三者共用模型版本、catalog 定義、schema 資訊、問題與澄清回覆、SQL guard、額度與資料快照；各自 prompt／模板差異公開。C 比 B 是整套系統比較，不能把增益全歸因於 planner 一個元件。

預先記錄各法的支援題型；不支援的任務保留在全體分母，另報共通支援子集。澄清回覆使用同一隱含需求的預定腳本，只對相關詢問回覆，不自動洩漏完整 gold。

主指標：最終任務成功數／總題數（含所有失敗）；分題型的數字、口徑與時間正確性；該澄清時有澄清／不該澄清時過度追問；無依據數值或因果宣稱；拒絕與 timeout 成功。附 API calls、token、USD、wall-clock median/p95、query duration、失敗類別。40 題的尾延遲只作此樣本描述。資料型別／排序／null／Decimal tolerance 在評估前固定。

每方法每任務跑一次，順序預先固定並交錯方法，cache cold/warm policy 明示。保留完整 terminal outcome，禁止刪除或重跑挑最佳。這是有限單模型系統研究，沒有跨模型、跨資料庫泛化結論。

正式呼叫前必須有實際 model id、provider、run manifest、價格來源與總預算。交接的第一個開發 session 不執行正式保留題，不自動建立付費服務。若 provider 無回報費用，標記不可得／依已記錄費率估算，不寫零成本。

## 9. 結案與後續

- 工程交付：獨立合成 DB 可從乾淨來源启动，開發契約案例通過；具 UI、證據、錯誤處理与離線 CI。
- 實證交付：完成一次凍結三方法比較、所有失敗保留、結果可核對；正結果不是結案條件。
- 發布交付：核對來源／授權／可公開內容，完成操作與機制展示；取得發布授權後建立正式 repo／release。

若正式研究揭露既定工程契約的實際 bug，可以修復並增加回歸；舊評估永遠保留，修正版只標工程修復。新一輪能力宣稱須另設版本與評估，不能將修復後重跑原題包裝成未見測試。

每階段可独立標記完成。需要憑證、正式評估或發布時，不把已完成工程重新標成半成品。新增模型、產業或功能要有具體收益假設，不能為了讓歷史 checklist 全綠而重開。
