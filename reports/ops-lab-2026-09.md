# 本機營運實驗：負載、故障注入與 24 小時 soak

2026-09-20 至 09-22，在同一個本機 Docker 堆疊、同一個 runtime image 上跑完三組量測。**負載：送出 3,374 次請求，2,481 次答對、0 次答錯，891 次在 2 rps 時被 HTTP 429 擋下（設計上的背壓）。故障注入：5 種情境各 3 次全部通過，恢復 7.7–20.0 秒。24 小時 soak：1,439 次請求全部答對，未觀察到程序重啟，RSS 從 85.5 MB 走到 94.2 MB 後持平。** 正常配置使用固定 1 秒的 mock provider，故障注入依情境調整；不是真模型；這是工程驗證，不是產品 SLA。

原始事件、回應與部署收據只留在本機 `.local/` 下，不公開；本文只發布摘要數字。堆疊與量測器的設計見 [docs/ops-lab.md](../docs/ops-lab.md)。

## 測了什麼

- 堆疊：`scripts/ops_deploy.py` 建立的獨立 Compose 專案。MySQL 8.4 在私有網路、不發布主機埠；app 容器是 `enterprise_query.ops` 包起來的既有 `Service`，uvicorn 單一 worker，只把 HTTP 發布到主機 127.0.0.1。QueryPlan、compiler、SQL 白名單、唯讀 executor 與合成資料都是原本的。
- provider：deterministic mock，每次規劃呼叫固定延遲 1.0 秒。問題固定為 2018 年 7 月 delivered GMV；量測器用自己的 oracle 核對答案（242 BRL、3 筆訂單、AOV 242/3，來自公開的合成 fixture）。
- 容量：同時最多 **4 個 active job**，超過立即回 HTTP 429 `overloaded`，沒有等待佇列。provider 呼叫由 `Service` 的 `asyncio.Lock` 序列化（[`service.py`](../src/enterprise_query/service.py)，`main` 上原有的設計）。mock 固定 1 秒，所以**理論吞吐約 1 rps**；每個請求另含 identity check 與一條 SQL，約 0.05 秒。
- 量測器：`scripts/ops_measure.py`，在主機上跑的獨立 HTTP client，不 import 服務程式碼。每個排程事件記 offered／sent／terminal；晚到超過 1 秒的排程記為 generator failure，不補發也不重送。resource 取樣每 30 秒讀 app 容器 PID 1 的 `/proc` CPU 與 VmRSS（程序 RSS，不是 Docker 的容器記憶體），並讀 `/ops/metrics` 與 `/health/ready`。
- 「完成」（`status: completed`）表示實驗跑完並產生摘要，不表示每一筆請求都成功。

12 格 = 0.25／0.5／1／2 rps × 3 次獨立重複，每格 300 秒、獨立 epoch；2026-09-20 14:00–15:02 UTC。p50／p95 是答對請求的 client 端延遲（秒，線性內插）。

**怎麼讀**：每一個 HTTP 200 都通過 oracle 核對，沒有答錯的答案。0.25 與 0.5 rps 的延遲就是 mock 的 1 秒加 SQL，queue 幾乎為零。1 rps 正好等於理論容量：沒有任何 429，但要排隊等 provider lock，queue p50 0.23–0.34 秒，所以 p50 升到 1.28–1.43 秒。**2 rps 是理論容量的兩倍：300 秒內送 600 次，每格共答約 300 次（303／302／302，包含窗口後 client tail，不能直接視為窗口內穩態吞吐），其餘約 50 % 立即收到 429 `overloaded`（拒絕延遲 p50 4.6 ms）。這是「最多 4 個 active job ＋ provider 序列化」設計出來的背壓，不是缺陷；答對請求的 p50 3.78 秒 ≈ 自己的 1 秒加上排在最多 3 個 job 後面的 queue 2.7 秒。** 12 格各自一個 epoch，每格結束都等 active_jobs 歸零再收最終 metrics。

其他數字：provider_seconds p50 1.001 秒、sql_seconds p50 0.047 秒；app 程序 CPU p50 4.8 %（一核 = 100 %）、p95 7.4 %；RSS p50 90.9 MB、p95 95.9 MB；DB 連線 1（含取樣器自己的短連線）。排程晚到 p95 0.02 秒，沒有取樣缺口。

兩筆 `transport_error` 都是 client 端 `RemoteProtocolError`：連線在 2–3 ms 內被關閉、沒有收到回應，伺服器端結果未知，依規則不重送。2 rps #2 那一筆之後，同一 session 的第二次請求因前一筆仍是 `work_pending` 而被量測器擋下（1 次 generator failure，原因 `session_still_active`），所以該格送出 599 而不是 600。這兩筆的原因沒有在證據裡確認，不歸因。

## 故障注入

5 種情境 × 3 次獨立重複，2026-09-21 16:16–16:25 UTC，每次以新 epoch 開始，注入前後都跑 oracle。「恢復秒數」從開始恢復（重啟 MySQL、回滾、重建 app 或恢復正常 mock 設定）算到就緒、oracle 再度答對、舊 epoch 被拒為止；只算到就緒的話是 6.6–18.9 秒。

| 情境 | 注入方式 | 注入期間觀察到 | 恢復秒數 #1 | #2 | #3 |
|---|---|---|---:|---:|---:|
| db | 停止 MySQL 容器 | `/health/ready` 503；請求回 HTTP 200、狀態 `execution_error`，沒有捏造答案；epoch 不變 | 18.1 | 17.9 | 12.9 |
| provider-slow | mock 延遲改 5 秒，送出 0.3 秒後 HTTP 取消 session | 取消回 200，但 active_jobs 仍 ≥ 1（provider 執行緒殺不掉，槽位到 mock 結束才釋放）；請求在 5.05 秒後回 `rejected` | 9.5 | 8.7 | 7.7 |
| provider-error | mock 每次規劃呼叫失敗 | 1.0 秒後回 HTTP 200、狀態 `provider_error` | 10.7 | 20.0 | 13.3 |
| kill | mock 延遲改 10 秒，確認請求在處理中後對該容器 ID `docker kill`（SIGKILL） | 請求在 0.34–0.36 秒收到 transport error；daemon 記到 signal 9、exit 137；3 次都是有效中斷；伺服器端結果未知、不重送 | 7.8 | 11.3 | 8.0 |
| rollback | 更新到刻意 unready 的 image（DB 埠設為 1），再回滾 | 更新以失敗收據結束；`/health/live` 200、`/health/ready` 503；對 unready 候選探測沒有答案 | 8.5 | 9.2 | 8.3 |

15 次全部 `passed`。oracle 探測 36 次：注入前後 30 次全部答對；MySQL 停止中與 unready 候選的 6 次都是預期的無答案。app 被替換的 12 次（db 以外），拿舊 epoch 再送請求都得到 409 `stale_epoch`；db 情境重啟的是資料庫，app epoch 保留，不適用。kill 的恢復是用同一個不可變 image 明確重建 app 容器，並確認新容器 ID、新 epoch 與 mock 設定回到 1 秒。

**先前三次失敗的嘗試。** 同一個 image、同一份 runtime source 之前跑過三次完整故障實驗，都失敗在 kill 情境，失敗都發生於 kill 步驟；後續變更限主機量測器，服務 image 沒有改過。第一次 Docker／Compose 暫態根因未確認，明確重建是恢復流程補強，不代表原根因已確診：
2026-09-20 15:02（量測器 `7b6c2c8`）db／provider-slow／provider-error 各通過 1 次，kill 第 1 次請求確實被中斷，但恢復用的是一般 `compose up`，指令回來後 app 容器仍是 exited，90 秒就緒等待逾時（RuntimeError）；修正 `0ab2ec0` 改為明確 `--force-recreate` 重建 app 並驗證新容器與新 epoch。
2026-09-21 13:38（`0ab2ec0`）15 次中通過 13 次（含 kill 第 1、2 次），kill 第 3 次在 5.29 秒的注入區塊裡，請求已在 1.05 秒拿到正確的 HTTP 200，根本沒被中斷，AssertionError；修正 `4cb1d52` 只在 kill 情境把 mock 延遲調到 10 秒、固定容器 ID、先確認請求在處理中才 kill。
2026-09-21 15:58（`4cb1d52`）通過 3 次，kill 第 1 次請求在 0.99 秒被中斷，但 `docker kill` CLI 沒在 3 秒內返回，TimeoutExpired、缺最終狀態證據，判失敗；修正 `22cd6f2` 把 CLI 回應（10 秒）與中斷證據（5 秒窗內的 transport error、daemon 的 signal 9 事件、exit 137）分開判定。
第四次（`22cd6f2`，上表）15 次全過。這三次失敗的目錄與收據都保留在本機，不重新分類；kill 的量測程序在 `4cb1d52`／`22cd6f2` 有改，負載實驗的排程、計時與 oracle 語意沒有動，所以 `7b6c2c8` 跑的負載結果仍適用。

## 24 小時 soak

2026-09-21 16:25:37 → 09-22 16:25:37 UTC，實測窗口 86,400.012653 秒，預定每 60 秒以新 session 送一次請求；實際建立 1,439 個唯一 session，另有 1 次漏發。窗口內觀察到單一 epoch。

| 項目 | 數字 |
|---|---:|
| offered／sent／terminal | 1,440／1,439／1,439 |
| HTTP 200 `answered`／答對 | 1,439／1,439 |
| sent 但沒有終態 | 0 |
| client 延遲 p50／p95／最大 | 1.050／1.124／1.927 秒 |
| provider_seconds p50／sql_seconds p50／queue p50 | 1.001 秒／0.046 秒／3.5 µs |
| resource 取樣次數／成功讀到程序 | 2,879／2,870 |
| process identity | 有效樣本中同一個（未觀察到重啟） |
| RSS 首次／p50／p95／最後 | 85.5／90.3／94.2／94.2 MB |
| CPU p50／p95／最大 | 0.33 %／0.47 %／3.3 % |
| DB 連線 p50／最大 | 1／2 |

**記憶體。** RSS 開場 1.5 小時內從 85.5 升到 90.3 MB，之後 11 小時停在 90.33 MB；接著三次約 1.1 MB 的階梯（04:53、08:45、09:19 UTC），09:44 之後到結束約 6.7 小時都在 94.20–94.24 MB。1,439 次請求共增加 8.7 MB，看不到隨請求數線性增長的外洩跡象；但只跑一次、一天，不能排除更慢的增長。伺服器端 metrics 到最後：admitted 1,439、coalesced 0、rejections 0，session 計數最高 30（30 分鐘保留 × 每分鐘 1 個），active_jobs 在 2,874 次讀取為 0、4 次為 1。

**三類量測異常；已送出的請求均正確，但缺失期間不能推定服務絕對可用。**
(a) 1 次 generator failure：2026-09-21 18:00:51 UTC（offset 5,700 秒）的排程晚到 13.8 秒，依規則不送、不補發，所以 sent 是 1,439 而不是 1,440。這記錄了主機量測器的排程落後；根因未確認。另有 3 次請求排程準時、但送出前被卡了 11–12 秒（同一時段的 17:06、17:33、17:46 UTC），還有 2 次晚 1.3–1.4 秒（18:41 與 09-22 09:14 UTC）；送出後都在 1.3 秒內答對。
(b) 9 次 resource 取樣讀 app 程序失敗（`TimeoutExpired`，RSS／CPU／DB 為 null）：7 次在 09-21 17:12–18:44 UTC，2 次在 09-22 08:17–08:18 UTC。這 9 次的 `/ops/metrics` 與 `/health/ready` 都是 200，同一分鐘的請求也都答對。
(c) 取樣間隔（正常 30 秒）拉長：以相鄰兩筆 resource 紀錄的時間差算，6 次超過 45 秒（46–66 秒），5 次在 09-21 17:26–18:44 UTC、1 次在 09-22 08:16 UTC。量測器自己的「超過 60 秒」偵測沒有觸發。另有 57 次取樣本身耗時超過 5 秒（最長 40 秒）：27 次在 09-21 17–18 時、30 次在 09-22 06–10 時（UTC）；取樣是經由 `docker exec` 讀 `/proc`，可能受主機負載影響，原因未確認。
(a)–(c) 包含主機排程與採樣缺口；現有證據不足以歸因於其他工作、主機負載或休眠。後續 HTTP 200 與正確回答只能支持觀測到的請求結果，不能填補未送出請求或缺失的資源樣本。CPU null 共 19 筆：初始基準 1、讀取失敗 9、失敗後重新建立基準 9。

**結束。** 視窗結束後量測器對 app 送 drain（`outstanding_jobs` 0、readiness 轉 503，這一筆取樣的 draining=true 是預期的），再依設計重建 app 容器恢復正常，得到新的 epoch。

**結論**：完成 24 小時量測窗口；1,439 次已送出請求全部答對，窗口內未觀察到 epoch 或 process identity 改變。但有 1 次漏發與 9 次資源採樣缺失，不能宣稱每分鐘無缺口的連續 24 小時驗證通過。RSS 增加約 8.7 MB，單次低負載觀察不足以排除記憶體洩漏。結果限於 mock provider 與合成資料。

## 限制

- provider 正常配置是固定 1 秒的 mock（故障情境另行調整），不是真模型：延遲、容量與故障行為都不代表接上 `gpt-5.6-luna` 的情況；真模型的延遲與費用見 [正式報告](formal-luna.md)。
- 單一主機、Docker Desktop on Windows；MySQL 與 app 都在同一台機器的容器裡，量測器也在同一台主機上。取樣器與服務共用主機，可能受資源競爭影響；本次異常原因未確認。
- 負載與故障各跑一輪、24 小時 soak 只跑一次；沒有跨日、跨機器的重複。
- 合成資料只有幾筆訂單，SQL 約 0.05 秒；不能推論真實資料量下的 SQL 延遲或 5 秒期限的行為。
- 資源數字是 app 程序的 RSS 與 CPU，不含 MySQL；DB 連線數含取樣器自己。
- 這是工程驗證，不是產品 SLA；結果不支持任何多租戶、無人監督或雲端部署的宣稱。

補充量測邊界：負載完整四項 timing 只涵蓋 2,481 次回答，兩次 transport error 的 server outcome 未知；soak 1,439 次 timing 皆完整。負載 735 筆資源樣本有 12 筆初始 CPU null，RSS／DB 無缺值。三次正式 kill 的 CLI 皆 completed；CLI timeout 被獨立證據接受的路徑只有回歸測試覆蓋，不能宣稱本輪已實測。
